Candidate A

Blueprint

Show the human what will be built, obtain approval, then verify that the build kept the promise.

This workflow consolidates the required lineage behavior. Do not run lineage or lineage-diff as separate workflows and do not produce their standalone text-chain renders. Read the code once, author one prospective artifact family, and reuse its approved AFTER world during verification. Consult skills/lineage/SKILL.md, skills/lineage/details.md, or skills/lineage-diff/SKILL.md only when this contract leaves a syntax or schema question unresolved.

1. Draft the prospective contract

Understand the request and inspect the code it touches. Pick one tracer: the value or symbol whose journey crosses the most changed code. Two disjoint journeys require two lineage tabs, not one crowded chain.

Trace once

Trace the current world from its real entry point (CLI command, route, event handler, cron) to its terminal effect (response, stdout, file, exit code). A mid-chain requested symbol is only the starting point for investigation.

Prefer a fresh graphify-out/graph.json skeleton when present:

python3 -c "import json,os; m=json.load(open('graphify-out/manifest.json')); d=[p for p,e in m.items() if not os.path.exists(p) or os.path.getmtime(p)>e['mtime']+1]; print(len(d),'of',len(m),'files drifted'); [print(' ',p) for p in d[:10]]"
graphify query "How does <entry> work end to end?"
graphify explain "<changed-symbol>"

Update graphify first if a traced file drifted. Otherwise use LSP/grep to locate symbols and targeted reads to verify only the selected hops, exact signatures, callers, and terminal effect. Do not reread whole files after those facts are captured.

Project the designed world from the same entry to the same terminal effect. If either boundary changes, use the nearest unchanged ancestor and descendant as anchors. For an entirely new flow, BEFORE contains the verified current anchors and their current path or absence of a path; AFTER contains the complete added journey. Never present a projection as a source fact.

Both worlds must be complete strict alternations of:

  • data objects — type plus fields that travel; independent inputs fan in as independent provenance branches
  • calls — exact Owner.method(params) → Return or function(params) → Return, followed by an active, concrete, roughly ten-word wtf line

Include decisions, outcome edges, per-item loops, side-channel effects of → None, and all hops from entry to terminal effect. Every substantially touched file must occur in a non-unchanged hop or be named as outside the tracer’s diff.

Verdict every hop

Give every BEFORE and AFTER hop exactly one verdict relative to this design:

  • unchanged — same symbol, home, mechanism, and chain position
  • changed — survives but signature, home, mechanism, or position changes
  • removed — BEFORE only
  • added — AFTER only

A rename is changed. Pair surviving counterparts with the same ID suffix. Mark every BEFORE fact as source-verified and every AFTER fact as either source-preserved or projected.

Author one artifact family

Write lineage.mmd as one flowchart LR with full BEFORE and AFTER subgraphs (direction TB) pinned by BEFORE ~~~ AFTER. Use IDs B_<module>__<hop> and A_<module>__<hop>. Preserve lineage shapes: cylinders for data, sharp boxes for free functions, rounded violet boxes for instance methods, deeper-violet stadiums for classmethods, dashed rounded violet boxes for staticmethods, diamonds for decisions, and stop styling for dead ends. Labels contain the exact signature and wtf line; details belong in the manifest.

Create one lineage.details.json. It is the sole semantic source for all tabs. Add an entry for every changed, added, removed, open, or deliberately inspectable item; undisclosed items are still navigable and default to unchanged gray. For each entry include every applicable fact:

  • label, verdict, kind, owning class, exact signature, params, returns, raises, doc, wtf, changed data fields, concise notes, and repo-relative source
  • both BEFORE and AFTER params, returns, and raises for every changed hop, so the drawer can diff the contract exactly
  • impact on every changed or removed hop: every caller outside the traced flow, gathered with graphify explain, with caller, where, note, and editor href when configured; use [] only after verifying there are none
  • open on every unresolved design choice; omit it only when resolved
  • integer order on every added or changed implementation item
  • flag: "no consumer" on every planned field no projected hop reads
  • views mapping the semantic entry to every node, class, participant/message, state, or entity that represents it in another tab

Use the repository editor template for source.href and impact links; default to absolute vscode://file/... links when no template exists, and omit href when the editor is configured as None.

Add only useful supporting axes

Lineage is mandatory. Nominate the following axes when their trigger fires, but draw one only if it answers a question the lineage does not:

Axis Mermaid type Trigger
Flow flowchart second command, background job, or error/control path
Sequence sequenceDiagram ordering, callback, retry, concurrency, or hand-off
Structure classDiagram new or reshaped interface
State stateDiagram-v2 new or changed lifecycle transition
Data erDiagram new or reshaped schema

Scope supporting diagrams to the delta and immediate neighbors. A sequence is one temporal zoom, never a lineage redraw. Name skipped nominees and why they add nothing.

Every diagram is a verdict diff. Every visible node, class, participant/message, state, and entity is gray unchanged, orange changed, red removed, or green added. Map all non-unchanged elements through views wherever the viewer supports that element type; for unsupported Mermaid element types, apply the same verdict class directly in the .mmd. Removed elements remain as red ghosts. Never leave a delta element unstyled, and never duplicate its explanation outside the shared manifest.

Done when the full prospective BEFORE/AFTER lineage exists, all touched files are accounted for, details/impact/open/order data is complete, and every tab visibly uses the same verdict language.

Do not restate the diagrams hop by hop.

3. Approval gate

Do not modify production code before explicit approval. Ask for one verdict:

  • Approve — lock these artifacts as the build contract and begin implementation
  • Revise — incorporate feedback, rerender, and return to this gate
  • Rethink — discard the approach and draft again

If a requested revision appears harmful, explain the trade-off briefly, then draw the human’s chosen design. Preserve the exact approved lineage.mmd and lineage.details.json; verification consumes them rather than reconstructing the promise.

4. Verify the complete post-build contract diff

After implementation, trace only the built world from source with the same tracer and boundaries. Reuse the approved prospective AFTER chain verbatim as contract BEFORE; do not retrace the original pre-build world.

Render a full side-by-side contract diff:

  • BEFORE — every hop from the approved projected AFTER chain
  • AFTER — every hop in built source from entry to terminal effect
  • unchanged — promise kept exactly
  • changed — promised hop exists but signature, home, mechanism, fields, exceptions, or position drifted
  • removed — promised hop was not built
  • added — built hop was never promised

Verdict every hop, preserve strict data/call alternation, include complete branches and fan-in, and verify every AFTER signature and source location. The contract details manifest must contain every non-unchanged hop, paired BEFORE/AFTER params, returns, raises, field changes, notes naming the exact drift, source links, and newly discovered out-of-flow impact. Render it with the same viewer and verdict styling; fix validation failures.

Report every non-unchanged hop in one sentence and either fix it or obtain explicit acceptance. Accepted drift becomes the new contract: update the blueprint artifacts only after acceptance so the saved record matches built reality. An all-gray, full-chain contract diff is the goal.

Done when the complete promise-vs-built page is shown and every drift is fixed or explicitly accepted.

Candidate B

Blueprint

Create one canonical design record, generate every view from it, obtain approval, then compare built source with the approved record. Do not independently author repeated Mermaid labels, verdicts, or drawer data.

Hard contract

Every run must produce all of these:

  1. a complete prospective BEFORE/AFTER lineage for one tracer, from entry to terminal effect;
  2. the same verdict for a semantic item in every diagram where it appears;
  3. complete signature, payload, impact, open-question, and build-order data for the delta;
  4. an explicit human approval gate before production code;
  5. a complete post-build diff of approved AFTER versus built source.

The canonical record is blueprint.ir.json. It is the only model-authored design artifact. Mermaid files, lineage.details.json, the text summary, and contract-diff inputs are deterministic generated artifacts.

1. Discover once

Read the request and the touched code. Choose the single value whose journey crosses the most changed code: the tracer. If the change has disjoint flows, create one flows[] entry per tracer; never crowd unrelated flows into one chain.

For each tracer, locate in current source:

  • the entry point: CLI command, route, event handler, cron, or equivalent;
  • the terminal effect: response, stdout, file, database write, emitted event, exit code, or equivalent;
  • every alternating data object and transforming call between them;
  • every substantially touched file, either on a non-unchanged hop or in outsideFlow with a reason.

Use graphify query, graphify explain, and graphify path when graphify-out/graph.json exists. First check graphify-out/manifest.json; update graphify if any traced file is newer than its manifest entry. Read source only to verify the selected hops, exact signatures, payload fields, callers, and terminal effect. Without graphify, use LSP and targeted source reads.

Trace current source once. Do not separately rediscover facts while drawing supporting diagrams.

Lineage rules:

  • alternate data object / call without gaps;
  • calls use exact names, owning class when applicable, parameters, return type, and annotated raises;
  • each call has an active, concrete wtf line of about ten words or fewer;
  • fan-in inputs remain separate provenance branches;
  • decisions have one edge per outcome;
  • loops are one labeled per-item region;
  • a None return names its side-channel effect;
  • a projected AFTER fact is marked projected, never source-verified.

For an entirely new flow, BEFORE is still present: set state: "absent", record the source-verified unchanged ancestor/descendant when they exist, and generate an explicit absent-flow node between them. Never silently omit the BEFORE world.

Done when both worlds are anchored entry-to-terminal (or BEFORE explicitly proves the flow absent) and every current-source fact has a file location.

Blueprint

Artifacts

  • <axis>.mmd — only supporting diagrams whose triggers fire and which add information

3. Author the full prospective lineage

Every blueprint uses a prospective diff, including an entirely new flow.

  • BEFORE is the complete current-source journey from entry to terminal.
  • AFTER is the complete intended journey from the same nearest stable entry ancestor to the same nearest stable terminal descendant.
  • For a wholly new flow, BEFORE contains the real nearest stable trigger and the explicit current terminal outcome (for example, “route absent → 404” or “command absent → parser rejection”); it must not be an empty world.
  • Every hop states in the cache whether it is source-verified or projected.

Both worlds strictly alternate:

  • data object: type plus fields that matter;
  • call: exact name, parameters, return type, and owning class for methods.

Show decision outcomes, a per-item loop once, and separate fan-in provenance branches. A → None call names its side channel in its wtf line. Every call gets one concrete, active-voice wtf line of about ten words or fewer.

Render lineage.mmd as one flowchart LR with BEFORE and AFTER subgraphs, each direction TB, pinned by BEFORE ~~~ AFTER. Use ids B_<module>__<hop> and A_<module>__<hop>; counterparts share the suffix.

Use lineage shapes:

  • data: cylinder
  • free function: sharp box
  • instance method: rounded box
  • classmethod: stadium
  • staticmethod: rounded dashed box
  • decision: diamond
  • dead end: stop node

Do not hardcode verdict colors in Mermaid. The viewer applies them from the shared manifest.

Assign exactly one verdict to every hop in both worlds:

  • unchanged: same symbol, home, mechanism, and chain position
  • changed: survives but signature, home, mechanism, or position differs
  • removed: BEFORE only
  • added: AFTER only

Every touched file must appear in a non-unchanged hop or in coverage.outsideLineage with a reason.

Done when both complete worlds reach their terminal effect, alternation is unbroken, every hop has a verdict, and file coverage closes.

4. Author details once and map every view

Create one sparse blueprint.details.json. It is the authority for verdict styling and drawers across all diagrams.

  • verdict, kind, class, exact signature, doc, and wtf
  • params, returns, and raises; every changed hop has BEFORE and AFTER values so the viewer can diff them
  • fields, each with its own verdict; set flag: "no consumer" on every planned field no projected hop reads

  • source.path and editor-template source.href when available; omit href when the configured editor is None
  • impact: every caller outside the traced flow that must adapt, with caller, where, note, and optional href; gather it per changed or removed symbol with graphify explain or call hierarchy
  • open: every unresolved design choice, one sentence; never hide uncertainty in prose
  • order: an integer on every added or changed unit of build work
  • views: all ids representing the item in lineage, flow, sequence, structure, state, or data; values may be arrays

Use B_... and A_... entries where both worlds contain distinct details. Matching suffixes pair the drawer entries. Undisclosed unchanged items remain navigable and default gray.

Therefore orange/green/red/gray verdict styling applies across every diagram, not only lineage. Do not repeat explanations or palettes in individual .mmd files.

Done when a cache-to-manifest check accounts for all changed signatures, impacts, open questions, build order, unconsumed fields, and all non-unchanged view ids.

  • changed after-shape items map to changed;

  • all lineage hops have verdicts;
  • all touched files are covered or explained outside lineage;

7. Approval gate

No production code may change before explicit approval.

Ask for one verdict:

  • Approve — lock lineage.mmd, supporting diagrams, blueprint.details.json, and the evidence-cache fingerprints as the build contract.
  • Revise — invalidate only evidence and views affected by feedback, update them, rerender, and return to this gate.
  • Rethink — discard projections but retain still-valid source evidence; redesign from the contract boundary.

If requested feedback has a material trade-off, explain it before redrawing, then implement the human’s choice. Approval applies only to the rendered artifact family shown at the gate.

8. Build with delta invalidation

After approval, implement in order sequence. After each build unit:

  1. inspect its source diff;
  2. invalidate cache entries whose fingerprints changed plus direct path boundaries;
  3. refresh only those signatures, edges, callers, and fields;
  4. record implementation evidence without rewriting the approved projection.

Unexpected files or mechanisms are contract candidates, not silent blueprint edits.

9. Full post-build contract diff

Always perform a complete contract diff after the build.

  • BEFORE is the approved blueprint’s entire AFTER chain.
  • AFTER is the built source’s entire entry-to-terminal chain for the same tracer.
  • Re-anchor only at the nearest approved unchanged ancestor/descendant when an endpoint changed.
  • Reuse unchanged cache evidence only after fingerprint checks; retrace every invalidated region and its boundaries.
  • Include every hop, not merely changed hops.

Verdicts are contract outcomes:

  • unchanged: promise kept
  • changed: promised hop exists but signature, home, mechanism, or position drifted
  • added: unpromised built hop
  • removed: promised hop was not built

Write and render contract-diff.mmd plus contract-diff.details.json with the same two-world grammar, complete details, and shared verdict styling:

<skills-dir>/lineage/scripts/render.sh -t "<change name>: contract" \
  -d contract-diff.details.json contract-diff.mmd

Require renderer OK or the complete fallback. Report every non-unchanged hop in one sentence. Fix drift or obtain explicit acceptance. Accepted drift updates the stored blueprint artifacts so the recorded contract matches reality, then rerun the complete contract diff. Done only when every drift is fixed or accepted and the final rendered diff is all gray.

Candidate D

Blueprint

A blueprint is an approved, inspectable contract. No production code may be changed until the human approves it.

This workflow optimizes total model tokens, not merely coordinator context. Specialists receive bounded packets, own disjoint facts, and return machine-shaped shards. No specialist receives another specialist’s prose or reloads all lineage documentation. A fact is model-authored once in blueprint.facts.json; diagram labels, the viewer manifest, summaries, and contract checks are projections of that ledger.

Contract that may not be reduced

Every run MUST produce:

  1. a complete prospective lineage with side-by-side BEFORE and AFTER worlds for one tracer (or a plain planned lineage only when no before world exists);
  2. one verdict for every hop and consistent gray/orange/red/green diff styling in every diagram;
  3. complete changed-hop params, returns, raises, fields, notes, source/projection status, out-of-flow impact, unresolved open questions, build order, and flag: "no consumer" where applicable;
  4. an explicit human approval gate before production edits; and
  5. after implementation, a complete contract diff from every approved AFTER hop to built source.

The lineage grammar is strict: entry point to terminal effect; alternating data objects and calls; fan-in inputs retain separate provenance; decisions retain every outcome; loops are traced once as labeled per-item regions. Calls use exact signatures and a concrete active-voice wtf line of about ten words or fewer. Methods always name their owning class.

1. Scope packet — coordinator only

  • touched or expected-to-touch files/modules;
  • target public symbols named by the request;
  • available Graphify manifest and freshness result;
  • artifact paths and editor-link template;
  • hard constraints and known decisions.

If the change has two disjoint flows, create two tracer records and later two lineage tabs. Never crowd them into one chain.

Run the Graphify freshness command from the lineage contract. If traced files drifted, update Graphify before using it. This deterministic preflight prevents every specialist from repeating repository discovery.

The coordinator gives specialists only scope.json, relevant file paths, their output schema, and their fact-ownership rule. It does not send conversation history, other shards, or full skill files.

2. Evidence wave — parallel, disjoint ownership

Current-world tracer → shards/before.json

  • state: lifecycle transitions;
  • data: schema/relationship changes.

Evidence-wave token rules

Each pass reads only nominated files, uses tool output rather than paraphrasing entire files, and stops once its schema is complete. It may return an unresolved id instead of exploring unrelated code. One retry is allowed only for schema-invalid output; semantic uncertainty becomes open.
